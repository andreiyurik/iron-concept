# ADR 0010 — Svelte 5 + TypeScript for the Browser UI

## Context

With the server in Rust ([ADR 0009](0009-rust-for-the-server.md)), the UI
needs a browser framework. ADR 0002's layout was three UI technologies —
LiveView for ~95% of rendering, a React island for the design-time editor,
and an ~80-line JS hook plus uPlot for mimics and trends. One stack is better
than three, and a SCADA UI has specific requirements that decide which:

- SVG mimics are the core artifact: 100–500 bound elements updating at up to
  10 Hz, drawn in Inkscape/Figma or generated by AI, committed to Git.
- Quality must be rendered, never hidden
  ([visual-system.md](../specs/visual-system.md)).
- The bundle ships inside the `iron` binary and must run on Pi-class hardware
  and in the edge agent's local fallback page.
- Level 3 custom widgets are written by automation engineers, not frontend
  specialists — and increasingly by LLMs.

## Decision

Svelte 5 (runes) + TypeScript, built with Vite, shipped as static assets
embedded in the `iron` binary. No SSR: the operator UI is an application, not
content.

- **One typed real-time protocol.** A single WebSocket: full state snapshot on
  (re)connect, delta frames afterwards. Message types are generated from the
  Rust domain types (JSON Schema → TypeScript), so the browser and the server
  cannot disagree about what a tag update looks like.
- **A widget is a Svelte component with a fixed contract.** It declares which
  tags (display) or commands (control) it binds; it receives
  `{value, quality, timestamp}` as reactive state. Display widgets MUST render
  quality; control widgets MUST reference a command definition — the
  [visual-system.md](../specs/visual-system.md) rules are unchanged, only the
  implementation language is.
- **SVG mimics keep the `data-iron-*` file format.** The binding contract is
  the public format; one Svelte `Mimic` component loads the SVG, binds
  elements, and patches attributes reactively. The standard symbol library
  ships as Svelte components with the same bindings.
- **The editor (Phase 3) is Svelte too**, design-time only, as before.
- **uPlot stays** for trends — the one non-Svelte runtime dependency.
- **Runes are the mental model**: a tag is `$state`, a derived value is
  `$derived`, a widget is a subscriber. That is the SCADA model, expressed
  directly.

## Alternatives

- **React** — larger ecosystem and LLM corpus. Rejected: hooks and JSX are a
  worse fit for engineers who write HTML/CSS/SVG; larger runtime; SVG is a
  second-class citizen in JSX. One stack outranks the larger ecosystem.
- **Server-driven HTML (htmx / Datastar over SSE)** — closest in spirit to
  LiveView, minimal JS. Rejected: gauges, trends, mimics, and the editor are
  client-rendering-heavy; we would end up with JS anyway, plus a second
  paradigm.
- **Leptos / Dioxus (Rust → WASM)** — single language end to end. Rejected:
  thin ecosystem and LLM corpus, heavy WASM bundles on Pi-class targets, and
  "one language" matters for the runtime, not the view layer.
- **SolidJS / Vue** — workable; no decisive advantage over Svelte, smaller
  (Solid) or comparable (Vue) communities, larger compiled output.

## Trade-offs

- Svelte's component ecosystem is smaller than React's (drag-and-drop, data
  grids, node editors). `@xyflow/svelte` exists for the editor; gaps are
  accepted and filled as needed.
- **LLMs frequently emit Svelte 4 syntax** (`$:`, stores) instead of Svelte 5
  runes. Mitigated structurally: the scaffold ships a skill file and
  reference components ([ADR 0011](0011-ai-native-surface.md)), and
  `iron validate` rejects widgets that break the component contract.
- Hiring pool: smaller than React, far larger than Elixir.
- The "non-frontend engineer edits LiveView templates" path is gone. Level 1
  and Level 2 users never write UI code (YAML dashboards, mouse); Level 3
  writes one component against one contract — an acceptable trade.
- Client-side state means reconnection and snapshot logic is IRON's to write
  and test. Hundreds of lines, owned, not a framework dependency.
- UI-framework independence is **not** claimed: until a second view adapter
  exists, it is a hypothesis, not a property.

## Revisit when

A Phase 3 editor requirement cannot be met in the Svelte ecosystem — then the
editor alone may use another TypeScript library, still in one language. Or a
measured bundle/latency problem on the reference hardware points at the
framework rather than at IRON's own code.
